# EuroClub App — Специфікація ціноутворення

**Статус: ПІДТВЕРДЖЕНО ПРАЦЮЄ (Кеп, 07.08.2026).**
Ця специфікація — джерело істини для логіки ціноутворення. Будь-яка зміна цієї логіки
робиться ТІЛЬКИ після явного підтвердження Кепа — не за здогадкою, навіть якщо щось
"виглядає як баг".

---

## Три типи замовлень

| Тип | route1 | route2 | Ціноутворення |
|---|---|---|---|
| В одну сторону | id рейсу | не передається (`undefined`) | Всі дані з API — бекенд рахує сам |
| Round-trip (конкретна дата) | id рейсу туди | id рейсу назад | Клієнт рахує тариф в 2 боки |
| Round-trip з відкритою датою | id рейсу туди | рядок `"-1"` | **Ідентично** звичайному round-trip |

**Ключове правило:** round-trip з конкретною датою і round-trip з відкритою датою мають
**повністю однакову логіку ціноутворення**. Єдина різниця між ними — значення `route2`
(реальний id другого рейсу, або `"-1"` як маркер "дата ще не зафіксована"). Жодних інших
розбіжностей у розрахунку ціни, тарифу чи суми немає.

---

## В одну сторону

- `price` в `createOrderNew` = `subtotal` — сума `getPassengerPrice(i)` по всіх пасажирах,
  кожен зі своєю знижкою (категорія → `trip.discounts` цього рейсу → ціна).
- Бекенд рахує все інше сам, дані завжди довіряємо напряму (`paid`/`status`/`needpay` —
  завжди живі, без жодного локального "заморожування").

## Round-trip (обидва типи — конкретна дата і відкрита дата)

**Клієнтський розрахунок (незалежно від route2):**

```
pricedAsRoundTrip = isRoundTrip (є реальний trip2) || openReturnPending (обрана відкрита дата)

perPassengerOneWay[i] = getPassengerPrice(i)   // one-way ціна пасажира i, зі знижкою
twoWayGroup = findTwoWayGroupPrice(perPassengerOneWay, fullFareOneWayPrice(trip), from.id, to.id, direction)

tariff = pricedAsRoundTrip ? (twoWayGroup.tariff ?? subtotal) : subtotal
total  = pricedAsRoundTrip ? (twoWayGroup.total  ?? subtotal) : subtotal
```

`findTwoWayGroupPrice()` (`src/priceEngine.ts`) — шаблонна таблиця round-trip тарифів,
підібрана по one-way ціні поїздки туди й напрямку (`ua`→EU чи EU→`ua`). Це та сама формула,
що використовувалась стабільно з 27.07 — під час сесії 06.08 її намагались міняти
(price=subtotal на бекенд, щоб той рахував round-trip сам) — **це було відкочено**, бекенд
такої логіки не підтримує так, як припускалось. Формула client-side лишається чинною.

**Що надсилається на бекенд:**

```
price: String(tariff)
route1: String(trip.id)
route2: isRoundTrip ? String(trip2.id) : (openReturnPending ? '-1' : undefined)
```

**Що НЕ залежить від `pricedAsRoundTrip`** (лишається на `isRoundTrip`, тобто тільки коли є
РЕАЛЬНИЙ trip2 — бо для відкритої дати цих даних просто нема):
- місця/seat-map другого рейсу (`selectedSeats2`, `place2`)
- час/дата другого рейсу (`dep2`, `arr2`, `ftime2`, `ttime2`)
- заголовок "оберіть місце туди" (`seatOutbound` замість `seatBooking`)

## Знижки пасажирів

- Кожен пасажир має `discount` — id обраної категорії з `trip.discounts` (масив, що бекенд
  віддає для КОНКРЕТНОГО рейсу — не глобальний список).
- `resolveDiscountId()` (`src/passengerPricing.ts`): ручний вибір на екрані бронювання →
  категорія зі складу пошуку (якщо вона Є в `trip.discounts` цього рейсу) → дефолт/повний
  тариф.
- Якщо обрана на пошуку категорія (напр. "Військовослужбовці з УБД") відсутня в
  `trip.discounts` конкретного рейсу — тихий фолбек на повний тариф (без попередження
  юзеру). Це очікувана поведінка: різні рейси можуть мати різний набір активних знижок.
- Назви категорій бекенд віддає двомовно через `" / "` (укр/рос + нім) — в UI показуємо
  лише частину до роздільника (`localizedDiscountName()`, `passengerPricing.ts`).

## "Відкрита дата повернення" — додатковий флоу

`route2 = "-1"` — маркер для бекенду "round-trip, дата ще не зафіксована". Ціна рахується
рівно як для звичайного round-trip (див. вище) — жодних винятків.

Окремо від ціни: після оплати юзер бачить на екрані свого квитка (`Ticket.tsx`) кнопку
**"Зафіксувати дату повернення"** — обирає дату (календар, діапазон: сьогодні → +180 днів
від поїздки туди) → надсилається mailto-лист на `euroclubbus@gmail.com` з даними замовлення
→ менеджер вручну додає реальний зворотний рейс на бекенді → застосунок автоматично починає
показувати його (без додаткового коду — `Ticket.tsx`/`OrderSuccess.tsx` вже вміють показувати
round-trip з живих даних бекенду).

Технічно це відстежується окремим Firestore-документом (`open_returns/{oid}`,
`src/openReturn.ts`) — не пов'язано з ціною, лише з UI-станом кнопки фіксації.

## Файли, що беруть участь у ціноутворенні

- `src/pages/Booking.tsx` — головна логіка: `pricedAsRoundTrip`, `tariff`, `total`,
  формування `createOrderNew`.
- `src/priceEngine.ts` — `findTwoWayGroupPrice()`, таблична формула round-trip тарифів.
- `src/passengerPricing.ts` — `resolveDiscountId()`, `resolvePassengerPrice()`,
  `fullFareOneWayPrice()`, `localizedDiscountName()`.
- `src/pages/Results.tsx` — прев'ю ціни на екрані результатів пошуку (та сама логіка, що й
  Booking.tsx, синхронізовано навмисно щоб прев'ю не розходилось з фактом).
- `src/orderStatus.ts` — `hasFixedReturnLeg()`, `passengerDisplayPrices()`,
  `payInfo()`/`surchargeInfo()` (статус оплати, окрема від ціноутворення тема).
- `src/store/index.ts` — `openReturnPending` (прапорець з Results.tsx в Booking.tsx).
